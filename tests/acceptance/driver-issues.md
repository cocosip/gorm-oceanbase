# go-oceanbase 驱动问题交接

2026-10-23 在同一 Oracle 租户实测，OceanBase **4.4.2.2**，
`go-oceanbase v0.1.1`，GORM `v1.31.2`。以下两项均已在不导入 GORM 的
[`driverissues/oracle_test.go`](driverissues/oracle_test.go) 中独立复现。
本仓库不修改基础驱动，不做参数转换或 SQL 包装来隐藏失败。

## 1. Oracle BLOB 不接受普通 []byte 参数

建表 `CREATE TABLE <owned> (ID NUMBER PRIMARY KEY, V BLOB)`，随后执行：

```go
db.ExecContext(ctx, "INSERT INTO "+table+" (ID,V) VALUES (?,?)", 1, []byte{0, 1, 127, 255})
```

期望：写入成功，读回字节完全一致。
实际：直接执行和 `PrepareContext` 后执行均失败，错误 **600**，
`cast to blob type not supported`。
在 GORM 矩阵中影响 `types.bytes`、`types.bytes.pointer_null`、`types.oracle_blob`，
两种执行方式合计 **6 项失败**。

对照：

- 同一 Go 驱动改用 `types.Raw` 参数，直接和预处理执行均通过，并逐字节读回一致。
- 同一租户 OceanBase Connector/J **2.4.14**，`setBytes(new byte[]{0, (byte)255})`
  写入成功，`getBytes` 读回为相同字节。
- Java `setBlob(SerialBlob)` 在该客户端报不支持；该客户端 API 结果不作为服务端证据。

定位：`go-oceanbase/internal/valuecodec/binary.go` 的 `EncodeParameter` 将普通
`[]byte` 编码为 wire type **252**、原始二进制；显式 `types.Raw` 使用 type **203**。
Connector/J 的 `OBByteArrayParameter` 将 Oracle 字节转换为十六进制文本，
`getColumnType()` 返回 `VARSTRING`（253）。需要在驱动层核实 Oracle 普通字节参数的
协议编码及 NULL/空值/大负载，不能在 GORM 层普遍把 BLOB 改成 RAW。

## 2. Oracle INSERT RETURNING 的独立 PREPARE 参数计数不一致

建表包含 `ID NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` 和 `V VARCHAR2(10)`：

```go
query := "INSERT INTO " + table + " (V) VALUES (?) RETURNING ID INTO ?"
stmt, err := db.PrepareContext(ctx, query)
// v0.1.1 在此处失败，尚未执行 stmt.ExecContext。
```

期望：PREPARE 成功，随后用 `"probe", sql.Out{Dest: &id}` 执行并返回生成主键。
实际：`oceanbase: invalid SQL binding: server parameter count`；GORM 事务路径还可能附带
`driver: bad connection`。影响 `oracle_prepared` 的 `crud.generated_batch`、
`crud.default_only`、`crud.associations`、`crud.hooks_soft_delete`，合计 **4 项失败**。

对照：

- 相同 Go SQL 直接 `db.ExecContext` 加 `sql.Out` 成功，主键大于零。
- 相同 Go SQL 包在 `BEGIN ...; END;` 中后，显式 PREPARE/执行成功并取回主键。
- Connector/J `CallableStatement` 的相同 PL/SQL 块取回主键成功；未据此声明
  Connector/J 裸 INSERT RETURNING 的独立 PREPARE 已验证。

定位：`go-oceanbase/internal/statement/statement.go` 的 `Prepare` 在
`int(header.Parameters) != len(plan.Slots)` 时丢弃连接并返回 `ErrBind`。
现有证据定位到驱动独立 PREPARE 的参数元数据处理；服务端实际返回的输入/输出参数计数
及与组合 prepare-execute 路径的差别，仍需驱动层确认。

## 复现与修复后复验

通过环境变量 `OB_ORACLE_DSN` 提供 Oracle 测试 schema 的连接信息，禁止提交真实 DSN。
以下命令会创建随机 `GD` 前缀的自有表并清理；需要建表权限。

```powershell
go test -tags=integration ./tests/acceptance/driverissues -count=1 -v
```

v0.1.1 实测：7 个子用例中 **4 通过 / 3 失败 / 0 跳过**。
失败为 `bytes_direct`、`bytes_prepared`、`prepared`；父测试同时显示失败，不重复计数。
未设置 DSN 时明确 skip，不代表驱动问题修复。该复现套件保留正常行为断言，
驱动修复前不会把错误当作预期成功；升级驱动后应全部通过，再执行完整 GORM 验收矩阵。

## 同租户确认的服务端限制

以下保持在 GORM 验收的 fail 中，与上述驱动问题分开：

| 操作 | Go 与 Connector/J 相同结果 | GORM 失败项数 |
| --- | --- | --- |
| `math.MaxFloat64` / `Double.MAX_VALUE` 写入 BINARY_DOUBLE | 1426，numeric overflow；普通值已通过 | 4 |
| 建 NCLOB 列 | 902，invalid datatype | 2 |
| 建命名 `TABLE OF NUMBER` 类型后用作表列 | 600，nested table type not supported；类型本身创建成功 | 2 |

这些结论只针对本次 4.4.2.2 租户的具体操作，不推广为全部 Oracle 浮点、LOB 或集合功能不支持。
